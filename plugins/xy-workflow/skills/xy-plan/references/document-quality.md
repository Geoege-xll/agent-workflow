# 计划文档质量：组织、精修与读者检查

用于起草或实质修改计划，以及 PM 保存／交接自查和现有唯一 QA 的计划审阅。
先沿用当前需求、批准、源文件与必要证据，不重新访谈，也不预读无关计划。
xy-plan 仅返回草稿，PM 是计划文件的唯一写入者；QA 只读并将问题交回 PM。
Light 仍按实际保存／恢复需要简化，不因引用本页而启用 Full、DAG 或独立 QA。

## 从已有事实组织正文

计划面向用户、实现者、QA 和后续恢复者，目的是让他们找到当前有效范围、判断依据与下一步。
先区分当前已批准需求、待定建议、上一次真实已验收基线与本次尚未验收内容。
检查已有材料能否说明目标、约束、接口、验收和必要取舍；只补实际缺口。
可由源码或既有证据查明的事实先查明；影响范围、行为或授权的未决选择沿用现有澄清／批准路径，
不要把猜测写成已确认需求，也不要为写作另设一轮问题清单或每节确认。

一个长期事实写在一个主题中。先说明读者当前可观察的行为、适用范围与例外，再写本轮已批准的变化和可观察的验收条件。Full 保留五项元信息及有实质内容的 `## 需求与验收`，其余小节按需使用。已验收声明须可定位已交付行为、版本与原始证据。字段及兼容方式见[稳定主题的写法](../../xy-workflow/references/plan-lifecycle.md#稳定主题的写法)。

## 按变化局部精修

优先处理有实际缺口或取舍的节，再核对目标与验收是否准确概括当前方案。
只修改受新事实影响的内容，不重印全文、不追加相互冲突的补丁、不堆叠每轮完成记录。
对会改变使用方式的需求，从一个实际场景写起：谁在什么条件下操作、会看到什么结果。如果失败会改变下一步，写清保留了什么、能否重试、从哪里继续。验收条件应当让另一位读者能亲手判断结果。一个普通间距修复沿用已确认样式和原验证入口即可。

按读者的决定取舍细节。面向消费者时说明使用目标和阻碍；涉及多人业务时写清谁有权限、交给谁；由 Agent 执行时说明谁授权、何时交回人处理。只写影响这项功能的角色与条件。先给出当前结论和适用范围。需要用户取舍的地方写明建议、影响和待谁确认，得到决定后原位更新。指标确实影响验收时才写测量起止、条件和口径。

稳定需求编号可以串起多个状态。原型交付后，需求指向具体 HTML 的状态；原型中相应的需求导航可定位到同一主题中的规则章节。设计先行时先保留已交付的页面及待确认事项，等对应规则真实存在再补链接。验收通过后，用实际结果和证据补记已交付行为。文档中只保留必要的结论与出处，长输出、工具日志及实现细节沿用其原位置。
同一事实选择一个正文归属。引用具体项目文档时使用可点击的相对路径，具体章节链接到真实标题或显式锚点。已有代码结构详见架构文档对应章节时，业务主题只保留本能力的取舍及其链接。删去不影响决策或恢复的重复解释。
缩写、状态与关键假设须可理解，未验证内容明确标注，不用空泛的“处理边界”“补充测试”代替具体结果。
同主题拟保存前，先按[计划生命周期](../../xy-workflow/references/plan-lifecycle.md#定位现有主题)
定位并编辑原稿。保留历史需求又供本轮原型评审时，按[需求 Markdown](requirements-markdown.md#current-source-and-prototype-coverage)
明确标出当前需求定义的范围；必要的历史内容和引用继续原地可读。

恢复入口可按“已验证／待验证／剩余工作／阻塞与下一步”分组，保留能继续工作的最小事实和证据入口。
它是当前任务状态的恢复投影，不另维护一份 DAG、执行日志或独立状态源。
阶段描述当前迭代。已验收版本与“验收结果与当前已交付行为”说明可继续依赖的基线；进行中的迭代仍可保留既有版本。
精简正文时保留真实批准范围、原型页面／状态与必要指纹、验收来源及仍有效的取舍。
替换失效内容前，确认唯一历史和完整证据可从既有位置或真实 Git 历史恢复并修复引用；
Git 不能恢复未提交或未跟踪资料，无法确认时保留原资料并标明历史边界。

## 在现有自查与唯一 QA 中检查读者理解

PM 自查和本轮既有唯一 QA 从计划正文及其必要证据引用回答以下问题，不依赖作者口头补充：

- 当前要解决什么问题，范围与非目标是什么？
- 哪些需求和验收条件当前有效，哪些仍待定？
- 已经验收的版本及实际行为是什么，与本次目标有何区别？
- 哪些成果已验证，哪些仍待验证或未完成，阻塞与下一安全动作是什么？
- 批准和验收分别依据什么可恢复证据，适用范围和必要原型关联能否定位？

同时核对标题下内容与其职责是否一致、阶段与交付描述是否冲突、有无未解释假设、重复或矛盾。
回答不清时定位缺失或误导的段落／引用，PM 在原节修正；实质范围变化才回到原有澄清／批准，
格式和表达修正不产生新业务确认。QA 沿用同一轮审阅与现有交接，不另建读者 Agent、报告、gate 或第二 Reviewer。
格式检查只能证明选定文档满足相应协议，读者检查只能发现理解缺口；二者都不授予批准、QA PASS 或交付状态。
保存与校验的触发时机、指定文件命令沿用计划生命周期，不按每次工具写操作重复检查。

## 方法来源与本项目取舍

- 用实际角色与场景串起行为、异常恢复及可观察验收，在已有主题和 HTML 原型中按需互相定位。[Open VibeCoding 的 PRD 写法](https://github.com/mileson/open-vibecoding/blob/0468ec937386e0fdccb093c8a81bf50f63fb4a57/skills/open-vibecoding-prd/SKILL.md) · [按读者选择文档内容](https://github.com/mileson/open-vibecoding/blob/0468ec937386e0fdccb093c8a81bf50f63fb4a57/skills/open-vibecoding-product-document/SKILL.md)

- 以持续编辑的主题页和明确关系链接积累知识，原始资料独立保留，目录提供发现入口。本项目复用 PROJECT、STANDARDS、主题和已有证据位置。[Karpathy 的 LLM Wiki 原始 Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- 将“当前行为”与“本次打算改变什么”分开表达，验收后只更新被改变的事实。[OpenSpec 的规格与变化](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)
- 沿用现有 PM 自查和唯一 QA，用读者问题检验范围、证据与下一步，并只修改有缺口的段落。[Anthropic doc-coauthoring 固定原文](https://github.com/anthropics/skills/blob/00756142ab04c82a447693cf373c4e0c554d1005/skills/doc-coauthoring/SKILL.md)
- 链接文字说明目标内容，在上下文交代遵循哪条规则、查看哪个交互或依据哪条决定。[Google 开发者文档交叉引用指南](https://developers.google.com/style/cross-references)
