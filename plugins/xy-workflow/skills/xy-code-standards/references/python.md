# Python 架构案例

在实际 Python 任务需要判断导入接口、入口拆分或资源清理时选读。通用方法见[架构设计与增量演进](architecture.md)，官方指南和固定上游示例见[来源记录](sources.md#python)。

## 用模块和函数组织逻辑，按作用域管理资源

- 无须跨调用保存状态时，可优先组合模块中的函数。例如由导入入口在 `with open(...)` 作用域内将文件交给解析函数，读取和解析结束或抛出异常时由该作用域关闭文件。若接收调用方已打开的文件对象，关闭责任仍按公开契约约定。从入口验证合法输入和解析失败，并确认由入口打开的资源能在两个分支释放。
- 项目已运行静态类型检查且确有多个来源需要遵守同一结构契约时，可考虑 `typing.Protocol`，只声明调用方实际需要的成员。例如解析函数只需调用 `read()` 时，先检查现有类型标注能否表达所需签名。静态类型检查之外，外部输入仍需在运行时按业务契约验证格式与内容。

## 从真实导入或入口确认边界

- 先查外部调用者使用的导入路径、关键字参数和文档。用项目现有的公开导出约定，按需通过 `__all__` 明示模块公开名称，以前导下划线表示内部实现。小型解析、转换或校验函数可留在所属模块。遇到已被实际调用的内部路径，先评估迁移影响再移动。参考 PEP 257，为公开调用说明输入、返回值、异常、调用限制及可观察副作用。
- 已有 FastAPI 项目可参考多文件教程。应用入口在 `main.py` 装配 `items.router`，路由声明前缀与所需依赖，`TestClient` 从应用路由验证成功、资源不存在和缺少请求依赖的响应。真实持久化操作由项目现有的业务或数据边界负责事务和回滚，仍从 HTTP 入口验证调用者看到的状态与响应。教程的内存字典和令牌用于演示框架装配。
- 已有 pytest 项目可按真实资源的生命周期拆分 fixture。需要独立清理的建表或写入应有对应的清理责任。若后续准备步骤失败，前面已成功建立的资源仍可由其 fixture 清理。把准备失败或测试失败作为验证点，确认项目支持的重试能在干净、隔离的状态下执行。简单数据可留在测试附近，继续使用项目现有运行框架和数据库策略。
