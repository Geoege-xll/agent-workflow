# 当前请求的需求、方案与原型确认

按 `product/WORKFLOW.md#business-confirmation-policy` 判断当前工作依赖哪项决定。Light 与 Full 是交付等级。明确的同请求决定可以来自用户本轮委托或之前的答复；PM 核对它指向的对象、内容、范围和条件，复用仍有效的决定，只问真正待决的一项。

1. **确认做什么。** 给用户说明目标、服务对象、范围与非目标、关键约束和可观察的验收结果。Full 先用已确定的范围、影响与验收依据完成规划覆盖及 xy-plan 草稿，说明主要工作、顺序、风险、验收和验收后的文档去向；随后确认当前需求（`requirements_approved`）。可把已明确的原型或直接开发选择随需求记录；尚未选择时给出有理由的建议，确认具体受影响表面。此选择只决定是否做原型。
2. **按需确认怎样工作。** 面向影响交付的实际分歧，用可验证的行为描述方案，例如谁有权操作、正常状态和失败恢复、是否保留输入、认证接口和兼容性、数据迁移及回滚。说明选项、后果和推荐；同次答复若已明确覆盖需求和方案，就分别沿用。关键行为或异常尚未确定时，先确认方案，再派发依赖它的原型或生产任务。无 UI 的高风险变更同样适用，直接开发或用户免原型只去掉视觉确认。可逆内部实现（如不改变验证语义的正则写法）由实现者决定；按冻结依据恢复现有间距、样式或文案时直接复用适用授权。
3. **按需确认实际页面。** 选择原型时，先由设计者依据已确认行为交付具体 HTML 和状态。PM 核对静态证据并展示真实页面；用户明确同意当前展示的页面后，才为对应范围和依赖指纹记录 `visual_approved`。选了原型或认可方案都不能代替这一步。若评审意见改变行为或范围，先回到受影响决定，更新同一主题后再修订相关页面。

普通讨论到对话结论为止；仅原型只解决设计范围内的行为与验收，交付获准的原型后结束。开发委托、宿主安全提示、独立 QA 以及最终本地合并的 confirm/auto 策略分别按原规则执行。

## 谁提出方案

PM 是面向用户的方案负责人。简单问题由 PM 直接提出选项、推荐和理由。技术或交互事实不足时，PM 可按需请负责该模块的工程或设计角色在现有权限内只读核实接口、状态及限制，返回可行选项、代价和依据；此时不写生产代码或正式原型。PM 综合这些意见，向用户提出一份明确推荐，把用户决定写回同一主题，然后才派发依赖它的正式设计或实现。只咨询必要事实，无需专设方案 Worker。独立 QA 审查已批准目标、方案和实际证据，不担任方案作者。只讨论或只要原型时仍遵守既有委托范围。

## PM 交接

用自然语言呈现完整决定信息后再提问；接受可明确对应所问内容的肯定答复，无需用户输入内部令牌。多个候选、跨请求或含义不明的“可以”只澄清其对象。仅当用户明示采纳一项明确建议时，“按你推荐的”才确定对应选择。PM 在同一需求主题区分目标、拟定方案、已确认行为、实际页面和已验证交付，注明真实批准出处；文件落盘、访谈、设计稿或 QA 结果都不产生用户授权。

依赖某个实质决定的任务携带 `solution_decisions` 及对应 `solution_approved:<id>@<sha256>`，用同一请求 ID、决定 ID 和完整决定正文限定批准。需求已有明确授权时，尚待用户选择的方案只拦住依赖任务；其余已就绪的工作遵循既有调度。改范围时核对受影响的需求，改重试或权限等行为时重开对应方案，纯视觉调整按原页面规则处理。记录和更新操作见[派发规则](dispatch.md)。

- An exceptional confirmation must be represented in the task pack and omitted otherwise:

  ```yaml
  additional_business_confirmation:
    name: <stable gate name>
    reason: <why the applicable decisions do not cover this exception>
    decision_scope: <what the user is deciding>
    options: []
    evidence: []
    resume_condition: <exact answer that resumes dependent work>
  ```

  It blocks only dependent DAG tasks and must never become a permanent default stage.
