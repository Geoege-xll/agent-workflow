# 计划文档质量：组织、精修与读者检查

用于起草或实质修改计划，以及 PM 保存／交接自查和现有唯一 QA 的计划审阅。
先沿用当前需求、批准、源文件与必要证据，不重新访谈，也不预读无关计划。
xy-plan 仅返回草稿，PM 是计划文件的唯一写入者；QA 只读并将问题交回 PM。
Light 仍按实际保存／恢复需要简化，不因引用本页而启用 Full、DAG 或独立 QA。

## 从已有事实组织正文

计划面向用户、实现者、QA 和后续恢复者，目的是让他们找到当前有效范围、判断依据与下一步。
先区分当前已批准需求、待定建议、上一次真实已验收基线与本次尚未验收内容。
检查已有材料能否说明目标、约束、接口、验收和必要取舍；只补实际缺口。
可由源码或既有证据查明的事实先查明；影响范围、行为或授权的未决选择沿用现有澄清／批准路径，
不要把猜测写成已确认需求，也不要为写作另设一轮问题清单或每节确认。

Full 保持普通 Markdown 的 5 项元信息和 6 个固定 H2 标题，按原顺序组织；
元信息各写一个当前值，专题说明用所属节的 H3。具体协议见
[计划生命周期](../../xy-workflow/references/plan-lifecycle.md)，起草形状见 `templates/docs/PLAN.md`。
不要为某个专题增加顶层节或另建摘要／附录状态文件。

## 按变化局部精修

优先处理有实际缺口或取舍的节，再核对目标与验收是否准确概括当前方案；最终保留固定节序。
只修改受新事实影响的内容，不重印全文、不追加相互冲突的补丁、不堆叠每轮完成记录。
每项有效需求保留可判断的结果与边界；方案描述实现责任、关键接口和依赖，具体规则与完整日志用现有引用承载。
同一事实选择一个正文归属，其他位置仅作必要引用；删去不影响决策或恢复的重复解释。
缩写、状态与关键假设须可理解，未验证内容明确标注，不用空泛的“处理边界”“补充测试”代替具体结果。

恢复入口可按“已验证／待验证／剩余工作／阻塞与下一步”分组，保留能继续工作的最小事实和证据入口。
它是当前任务状态的恢复投影，不另维护一份 DAG、执行日志或独立状态源。
阶段描述当前迭代，已验收版本与第 5 节描述已有基线；二者可以分别为 active 和既有版本。
精简正文时保留真实批准范围、原型页面／状态与必要指纹、验收来源及仍有效的取舍。
替换失效内容前，确认唯一历史和完整证据可从既有位置或真实 Git 历史恢复并修复引用；
Git 不能恢复未提交或未跟踪资料，无法确认时保留原资料并标明历史边界。

## 在现有自查与唯一 QA 中检查读者理解

PM 自查和本轮既有唯一 QA 从计划正文及其必要证据引用回答以下问题，不依赖作者口头补充：

- 当前要解决什么问题，范围与非目标是什么？
- 哪些需求和验收条件当前有效，哪些仍待定？
- 已经验收的版本及实际行为是什么，与本次目标有何区别？
- 哪些成果已验证，哪些仍待验证或未完成，阻塞与下一安全动作是什么？
- 批准和验收分别依据什么可恢复证据，适用范围和必要原型关联能否定位？

同时核对标题下内容与其职责是否一致、阶段与交付描述是否冲突、有无未解释假设、重复或矛盾。
回答不清时定位缺失或误导的段落／引用，PM 在原节修正；实质范围变化才回到原有澄清／批准，
格式和表达修正不产生新业务确认。QA 沿用同一轮审阅与现有交接，不另建读者 Agent、报告、gate 或第二 Reviewer。
格式检查只能证明选定文档满足相应协议，读者检查只能发现理解缺口；二者都不授予批准、QA PASS 或交付状态。
保存与校验的触发时机、指定文件命令沿用计划生命周期，不按每次工具写操作重复检查。

参考 Anthropic 官方

全文去重／矛盾检查及面向读者问题检验理解的方法。
本项目只采用这些写作判断：不安装或执行第三方 Skill，不复制其全文，不引入新的发现入口、依赖或记录格式；
不采用固定数量访谈／选项、逐节确认、占位文档、任意完成阈值或多读者子代理流程。
原有需求确认与适用的最终视觉确认保持原职责，PM 独写计划，既有唯一 QA 承担独立审阅；没有新增批准或验收阶段。
