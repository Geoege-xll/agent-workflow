# Go 架构案例

在实际 Go 任务需要判断包、调用方接口或错误边界时选读。通用方法见[架构设计与增量演进](architecture.md)，官方依据见[来源记录](sources.md#go)。

## 从包和调用点确定公开边界

- 根据实际导入关系组织包。命令的启动与参数装配可留在现有 `main` 入口，同一职责的实现可放在同一个包。只在有相应模块布局和导入限制需求时使用 `internal`。稳定的单一实现可直接通过具体类型或函数协作。
- 多种来源确实共享调用方所需的行为时，优先复用合适的小接口，例如 `io.Reader`。需定义新接口时，从消费方实际用到的方法确定范围。类型通过方法集隐式满足接口，构造入口仍可提供具体类型。

## 文件输入与错误处理

- 例如导入命令用 `os.Open` 打开文件，检查打开错误后在文件所有者所在作用域用 `defer` 安排关闭。若导入还支持标准输入，解析函数可接受 `io.Reader` 并由调用方保管连接或文件的生命周期。显式检查读取和解析返回的错误，按项目契约附上必要的操作上下文。
- 如果公开契约允许调用方通过 `errors.Is` 识别底层错误，且支持版本提供该能力，可用 `%w` 保留底层错误。可被调用方识别的底层错误会成为 API 的一部分，错误是否向外暴露按已有契约决定。沿真实入口核对有效文件、文件不存在和内容无效时的结果与错误，并确认入口打开的文件在解析退出后释放。
