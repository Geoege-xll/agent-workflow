# 插件工作流审计闭环

- 主题 ID：`workflow-closure`
- 阶段：`active`
- 模块：任务图、QA 交接、Git 工作树交付
- 任务等级：`Full`
- 已验收版本：`local-task-pool-capacity-20-9fbe42c`

## 目标与范围

维护 PM 的需求调度、确认依据、单一独立 QA 及交付边界。当前迭代将 Light／Full 的交付强度与用户实际需要决定的事项分别判断。原型、QA 与 Git 交付保持各自的授权范围。

## 需求与验收

本轮经用户确认，在三个宿主的共用入口区分单项请求的交付范围。需求讨论只澄清与归纳，任务交错、上下文压缩和简短认可均不能扩大委托。仅交付原型的请求在设计验收后结束；已委托完整开发的请求，依据当前需求、适用方案及视觉确认放行对应实现。已有任务按各自授权继续。

验收使用同一句自然语言认可的正反对照，核对真实调度资格、实际文件变化及请求归属。确定性回放与官方客户端实际观测分别记录。宿主专属的安装与来源配置继续由安装主题单独维护。

后台 Reviewer 遇到 Claude 明确报告上下文耗尽且压缩未产生摘要时，PM 保留缺失回执的事实，按既有恢复入口决定能否继续。原样重放已耗尽的会话不能构成恢复。日常取证限制一次带入的输出和无关规范内容，保留当前请求要求的完整覆盖、冻结输入、有效证据与唯一 Reviewer。

### 两档交付与按需确认

- REQ-006：仅使用 Light 和 Full 两档。PM 分别确认交付目标与范围、影响行为或交付的方案选择，以及需要评审的实际原型。只需复用已确认页面的修复直接按已有授权进行。
- REQ-007：待决事项阻挡依赖它的设计或实现，同请求内独立工作可以继续。明确认可的同一决定可复用；更改内容或更换请求须重新取得相应依据。
- REQ-008：同一主题原位维护目标、规则和技术取舍、原型及验证后的维护入口，避免为单次确认或普通符合性修复建立新文档。用手机号登录、后端重试策略和间距修复分别验收。
- REQ-009：PM 负责对用户提出方案，需要专业事实时在当前授权范围内请相应 Agent 只读核对，给出建议和依据。用户确认取舍后，依赖该决定的原型或实现才动工。验收由独立 QA 承担。
- REQ-010：等待原型、视觉确认或基础阶段 QA 的开发任务，从调度、正式交接和交付登记三个入口得到一致结果。同一方案跨记录变更或撤回时，依赖它的任务遵守相同决定，独立请求继续。用户认可的具体页面和例外理由可以通过正式入口交接。
- REQ-011：独立 QA 拿到本次已批准的方案正文和可追溯的依据。修改已审业务行为会使对应的最终回执失效；PM 按批准范围补记验收事实后，仍可核对原受审内容并继续交付。隔离交付覆盖 PM 负责的架构文档，原型状态链接指向实际 HTML 锚点。

### 持续接单与任务池

- REQ-012：PM 能按当前项目及主会话恢复已委托的任务，按名称找到原记录。只讨论的需求保留在对话中；任务的当前状态、批准和执行者以原记录为准。
- REQ-013：用户可撤回待派工作，或要求停止运行中的工作。PM 区分已请求和已停止，保留实际改动与未确认的占用。更改运行中任务时，新的执行结果须对应已交付的修订。独立工作继续按自身条件派发。
- REQ-014：Codex 的只读复核和证据任务完成时，由原生生命周期事件触发 PM 核对当前绑定、最新任务包和结果证据。满足原有验收条件后，通过正式结算入口登记 `RESULT_VERIFIED` 并释放任务池占用。池满时，验证释放后可领取并启动下一项，无需用户追加提示。
- REQ-015：未确认的停止信号、身份或任务修订不符、缺少有效证据都保留原记录状态。重复或乱序事件不能重复结算。Writer 的构建验收和唯一独立 QA 沿用现有入口，宿主 Hook 沿用原生信任流程。
- REQ-016：任务池默认并发上限为 20。当前仓库配置和三端随包的新项目模板采用相同值。实际派发还受宿主实时容量、项目覆盖值及 Writer 和路径配额约束。验收核对三端模板、现有项目覆盖、20 个槽位的边界和较低的宿主容量。

并发领取和修订检验参考 Open VibeCoding 的实际用例。该工作流使用宿主返回的原生执行证据核实停止。操作示例见[PM 持续接单与调度](../usage.md#pm-持续接单与调度)。[上游并发用例](https://github.com/mileson/open-vibecoding/blob/0468ec937386e0fdccb093c8a81bf50f63fb4a57/test/open-vibecoding-task-runtime-concurrency.test.js)

## 方案与原型关联

用户以「直接增加一倍 20」批准默认并发上限 20。配置变更使用已有 `max_concurrent_subagents` 入口。当前请求只调整总并发值。已配置的项目按自己的适配器执行，任务池登记容量、现有审批与独立 QA 按原有规则执行。

Codex 自动结算属于非 UI Full 修复。Codex 原生生命周期 Hook 触发主会话对账。主会话以真实原生完成状态为准，核对任务证据后复用已有 `settle`，保留同一权威任务记录及其并发校验。实现者交付 Codex 候选及有针对性的打包回归，独立 QA 核对实际满池、结算和后续派发证据，以及 Claude Code、AGY 的相关入口。候选可通过官方宿主停用或回退，任务记录沿用当前格式。

批准依据来自本请求中的「批准修复方案，开始修复。保持现有审批和独立 QA，修完用 Codex 真实新会话验证自动结算、释放名额后能继续派发，再回归 Claude Code 和 AGY」。

PM 先确认目标与交付范围，依据现有事实提出方案。需要由用户取舍的行为、异常或影响交付的技术选择，随已有主题维护。PM 在明确批准后放行依赖任务，需要视觉确认时链接获准的具体 HTML 和状态。方案、视觉、构建与 QA 分别提供各自依据。普通局部修复沿用既有基线。示例见[两档交付与按需确认](../usage.md#两档交付与按需确认)。

#### 会话抽查的两个重点

1. **重复读取与上下文占用。** 按任务和执行者抽取代码、文档、技能及工具输出，核对内容版本、读取范围和当时用途。重点查同一内容反复载入、只需一节却读取整份、向子代理复制无关历史。文件更新后的复读、压缩后的恢复和独立 QA 取证分别判断。记录可定位的调用和可避免的输出量；有宿主用量数据时区分输入与缓存，无法归因到单次读取时只报告次数和字符量。
2. **PM 调度是否符合委托。** 沿用户指令、任务登记、原生子代理派发与回执核对实际行为。抽查讨论或等待期间有无越权启动，任务交错时能否继续接单，独立工作能否并行，重叠工作能否追加给合适的执行者，以及应做的独立 QA 是否完成。每项注明符合、偏离或证据不足，并定位到对应会话事件。

**Quotio 测试范围抽查。** 两项独立委托各有一个原生 Apple 实现者和一个只读 QA。界面任务执行了指定的一条导航用例。清零任务的包指定五个测试类，第一轮覆盖四种数据来源、迁移和存储等改动；实现者随后修改本地化文案，再次运行相同五类，两份 Xcode 结果各为 65 项通过。第二轮命令没有说明文案怎样使这 65 项结论失效。修复应让实现者核对改动对应的构建、实际资源加载和仍有缺口的行为，QA 按实际输入核对复用依据。[验证范围与证据复用规范](../../platforms/shared/skills/xy-build-verify/references/verification-scope.md)

**上下文取证。** 抽查至该 Claude 主会话第 1107 行时，六对 Read 返回了完全相同的正文，其中验证规范为 21,295 字符，任务图规范为 11,052 字符。两份长文的两次读取之间发生了上下文压缩。应检查恢复时所需的具体章节，不能把再次返回的字符数直接换算成浪费的 token。

当前 Codex 会话也出现了可避免的开销。定位一份已知名称的 RC2 回执时，文件搜索递归列出了整个候选构建目录，产生了被截断的长结果。直接核对该回执的路径即可回答当时的问题。此轮的三个开发实例均使用独立上下文，任务池登记及身份绑定晚于实际原生派发；这次记录可用于核对执行进度，无法证明领取先于派发。

其他发现由 PM 依据用户已确认的需求和实际交付影响评估优先级。例如，插件自身的权限重试若阻断业务派发，归入调度问题，记录阻断位置与后果。

修复遵循[通用代码规范](../../platforms/shared/skills/xy-code-standards/SKILL.md)。从会话证据追到实际入口、调用方和负责该行为的模块，再确定改动范围。多个入口若因同一规则分散维护而反复出错，应收拢规则并清理失效分支；宿主特有行为由对应适配层处理。独立 QA 从原故障入口复验，并核对受影响调用方的既有行为。

修复后按以上两项抽查本项目对应的 Codex 维护会话，以“先记录，等完成指令”和随后授权修复的消息为界按需取证。再在实际加载修复版的 Codex 新会话重测相关场景，分别记录历史行为和新版结果。
