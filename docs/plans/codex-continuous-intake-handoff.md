## 用户目标

本项目已经实现 PM、原生子代理、任务依赖、验证和 QA 编排。本次讨论不是重新建设这些能力，而是补齐 Codex 中与现有 Claude Code 用法相近的持续交互体验。

用户报告当前 Claude Code 可按以下过程工作：

1. 用户向同一个 PM 下达需求 A。
2. PM 派发 A，子代理在后台开发。
3. A 尚未完成，用户仍可以和同一个 PM 讨论，并下达独立需求 B。
4. PM 接收并安排 B；具备授权、容量及独立写入范围时，A、B 同时推进。
5. PM 接收两边的进度、阻塞和完成汇报，并分别验收、汇报。

目标是在 Codex 中实现上述效果。用户在 Codex 中遇到后续需求被阻断，但本轮没有采集发生阻断的实际会话事件，尚未判定消息是在客户端排队、PM 等待中延迟处理，还是在任务准入或容量检查中等待。

以下做法都不能单独满足目标：一次性批量派发 A、B；等 A 完成才处理 B；要求用户为每个需求手动新开聊天；仅增加子代理数量。

## 初步审计发现

### Codex 规则缺少运行中接收新需求的明确处理契约

相关入口：

- [Codex 平台适配](../../platforms/codex/references/pm-integration.md)：规定原生子代理派发、独立上下文、续用和实例生命周期。
- [Claude 平台适配](../../platforms/claude/references/pm-integration.md)：明确后台 Agent 执行及完成通知，避免前台睡眠循环。
- [共享实施与 QA 规则](../../platforms/shared/skills/xy-workflow/references/implementation-and-qa.md)：要求执行期间继续派发无关 READY 任务，但没有完整描述用户新增需求的接收过程。
- [工作流 Skill](../../platforms/shared/skills/xy-workflow/SKILL.md) 与 [产品权威规则](../../product/WORKFLOW.md)。

这属于规则缺口，尚不是实际阻断根因的运行时证明。建议补齐：

- PM 收到运行中消息时，区分新增需求、原需求修订、状态询问、取消或停止。
- 独立需求 B 保留 A 的执行、实例、状态、锁及证据；不因收到 B 重启或替换 A。
- B 按现有 Light／Full 与批准规则处理，具备条件即派发，不以 A 收口为前置依赖。
- 容量不足不阻止需求讨论和准备，只延迟实际派发；说明具体等待原因。
- 状态询问只触发必要汇报，随后继续协调；取消只影响明确指定范围。
- 用户新输入和子代理事件都应触发调度评估。使用宿主可用的原生通知与等待，不靠固定频率轮询或睡眠循环。

产品语义先维护在唯一权威，再由共享 Skill 和平台入口引用，避免复制出多套规则。

### 现有记录工具不提供向已有图直接追加新请求的完整入口

- [task_graph_init.py](../../lib/task_graph_init.py) 的初始化逻辑把任务统一绑定到本次 `request_id`；当时位置约为第 264 行。
- [task_graph_records.py](../../lib/task_graph_records.py) 的 `update` 只修改已有任务，拒绝未知任务 ID；当时位置约为第 269 至 284 行。

内存实验使用现有完整测试夹具，尝试更新不存在的 `new-b`，结果为 `unknown task ID: new-b`，原记录任务数量保持不变。实验未写入真实任务或文件。

这不表示 PM 完全不能接收 B：它仍可为 B 创建独立记录。缺少的是对持续接单路径的明确约定和覆盖。

建议优先评估每请求独立 Full 图或 Light 单包，保留各自批准、核心 pin、规范及 QA 依据；暂不直接拼成长期增长的总图。该建议尚未定案。

### 独立请求需要共享容量和冲突信息

[task_graph.py](../../lib/task_graph.py) 中的 `ready_tasks` 和 `effective_dispatch_capacity` 已有活动路径、语义锁及容量判断，可优先复用。

它们仅能检查调用者传入的数据。若 A、B 各有记录，计算 B 时漏掉 A 的资源占用，就可能超派发或产生写入冲突。因此需要核对升级后是否已有跨请求活动记录的汇总机制。

建议如有必要新增轻量查询：读取当前 PM 管理的活动记录，汇总 Full、Light、必要 QA 的锁和真实宿主占用，返回可派发项及等待原因。派发前复核状态并保护容量领取；记录仍以现有请求任务为权威，不另建重复状态机或 Agent 池。

多 worktree 场景要区分实际执行目录与共享资源。不同 checkout 中相同相对路径不必然冲突，共享分支交付、服务、数据库或语义资源仍可能冲突。不能未经设计就机械合并路径字符串。

### 合并请求时不能共享批准标记

`ready_tasks` 检查传入的 `approved_gates`；当前通用需求批准名为 `requirements_approved`。

内存实验构造 `req-a` 的运行任务和 `req-b` 的待执行任务，二者都声明该门禁；传入共享批准集合后，独立路径的 B 被返回为 READY。

该结果说明直接合并请求及批准集合有风险，不证明现有隔离记录已经发生错误授权。建议保留请求级批准，跨请求只共享容量和冲突信息；若选择合并模型，必须先设计按请求及必要指纹隔离的授权机制及迁移方案。

### 等待规则和能力诊断需要覆盖完整交互

- [manager/capabilities.py](../../manager/capabilities.py) 目前区分文档、源码观察及未实测状态，但尚未覆盖持续接单的完整验证。
- [Codex 配置生成器](../../lib/hosts/merge_codex_config.py) 已写入 `agents.enabled = true` 和 `max_concurrent_threads_per_session`；当前项目不是单纯漏开多代理。
- [project.yaml](../../project.yaml) 的项目并发上限不是实际会话配额保证；应结合宿主真实能力计算。

建议诊断分别说明：原生子代理是否可用、当前输入采用 queue 还是 steer、等待期间能否及时处理用户消息、原任务是否持续执行、主轮次结束后的通知和生命周期是否实测。

不得用停止主轮次代替 steer，也不得未经实测要求 PM 派发后立即 final。先验证主轮次结束或中断对子代理的影响，避免为释放输入框而丢失执行或后续收口。

## 推荐的实施分段

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| 宿主行为验证 | 在用户实际客户端启动可控子代理 A，A 运行期间向同一 PM 提交 B；分别观察 queue、steer 和等待 | 明确输入送达、PM 处理、子代理派发的时间顺序及 A 是否持续运行 |
| 规则补齐 | 产品规则、共享 Skill、Codex 平台细则补齐持续接单及消息分类 | 不停止 A 即可处理 B；所有必要确认、QA、版本固定和所有权边界保留 |
| 调度与记录 | 复用或补充跨请求资源汇总、准入和具体等待原因 | 不超容量、不重复派发、不串用批准；Light 不被强制升级为 Full 图 |
| 诊断和回归 | 更新能力说明、相关行为测试及原生验收步骤 | 静态合同、工具算法和真实宿主交互的证据分别记录 |

若实测确认客户端只能排队，规则修改不能改变客户端消息送达机制。此时再评估 App Server 接入层的必要性与维护成本；不要把常驻调度器或新 UI 作为第一步，也不要把需要用户手动切换多个聊天当成目标已完成。

若引入接入层，必须正确区分活动轮次 steer 与空闲轮次 start、处理轮次变化竞态、订阅真实完成事件并避免消息或任务重复派发。App Server 可用性与稳定性按届时官方说明重新评估。

## 必须覆盖的验收场景

1. A 尚未完成时提交独立 B，B 在 A 完成前开始执行，A 未被停止、重启或重复派发。
2. A 运行期间讨论尚未批准的 B，PM 可正常讨论，但不会提前实施 B。
3. A 占用某路径或语义资源时，冲突 B 等待，无关 C 可推进。
4. 名额用尽时可接收 C 并解释等待，资源可用后再次评估；不以伪造依赖表达容量等待。
5. A 失败只阻塞相关依赖，独立 B 继续；取消 B 不停止 A。
6. A 的需求批准、视觉批准、验收或 QA 不自动适用于 B。
7. 状态询问不改变执行范围；修订 A 时明确区分修订和新增 B。
8. Full 与 Light 并行时共享容量与冲突约束，各自保留必要验证和独立 QA 分支。
9. 每请求 QA 和汇报不等待无关请求；共享文件提交、worktree 集成按现有规则受控执行。
10. 压缩、恢复、断连或重启后不重复派发；核心升级不把运行中的 A 偷换到新 pin，新 B 按当前合法准入规则选版。
11. 主轮次结束、停止与子代理完成通知的实际行为单独记录，不从 API 名称推断生命周期。

原生验收至少保留客户端和宿主版本、实际输入模式、A/B 的请求与实例标识、消息接收及派发顺序、完成状态和必要验证证据。只采集本次授权的测试，不读取其他 Agent 的私有会话来充当进度证据。
