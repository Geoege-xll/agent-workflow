# UI 设计与 QA 审计整改

- 主题 ID：`ui-qa-audit-remediation`
- 阶段：`completed`
- 模块：QA 验收、微信项目识别和共享技能
- 任务等级：`Full`
- 已验收版本：`3.0.7`

## 目标与范围

关闭已确认的 UI 设计、移动端、内置 QA 技能审计问题。验收覆盖通用 QA 回执、普通 Full 的请求验收、三端包内技能和无 npm 的微信原生识别。保留现行两步确认及适用的原型验证，保持单一独立 Reviewer 的原生调度。交付范围为本地候选。

## 需求与验收

- REQ-001：QA 回执校验以冻结任务包为权威。PASS 必须覆盖必需 Skill 与强制审计面。普通与原生入口一致拒绝重复或非法 JSON。原生结果单次携带有证据的发现、验证与返工角色。
- REQ-002：普通 Full 的最终 QA 绑定 PM 事前冻结的完整差异、当前受审 Writer 闭包、契约和验收证据。旧包、旧回执或写入者返工后的旧状态不能被当作当前通过。仅相关变化使验收失效。同一 Reviewer 复核受影响部分，保持 Foundation、Light 与隔离工作树的已有有效流程。
- REQ-003：微信原生小程序在有效编译类型、模块内入口清单与代码齐备时，不依赖 `package.json` 即可识别。保留普通 Web、桌面、游戏、插件和无真实入口的识别边界。
- REQ-004：设计、移动与 QA 技能明确使用插件规范路径读取参考。原型评审协议集中到反馈合同。QA 审查 Writer 的生产 UI 投影，按真实运行端和适用原型政策取证，保持已有 Light 字段及免原型路径。

## 方案与原型关联

回执协议与状态绑定分责实现并用同一真实入口验证。微信发现与 UI 技能按当前共享规则维护。涉及工作流指令、资源和本地验收逻辑，沿用现有设计权威，不产生新产品原型。

## 当前进展与恢复入口

整改已通过独立只读复核和正式 `accept_request`。原审计的定向回归、三端候选验证及反例保留于 `/private/tmp/xy-ui-qa-skill-audit.S38RFa`。后续发行和本机状态由 [发行主题](stable-product-release.md) 维护。

## 验收结果与当前已交付行为

- QA 核对当前任务包的必需 Skill 和强制审计面。普通和原生入口共用严格解析，同一份回执可返回问题、证据、返工责任和验证结果。
- 普通 Full 由 PM 预先冻结完整差异，`accept_request` 同时绑定开发任务、实际变更文件、验收证据及原 Reviewer。相关变化使旧回执失效。真实 Git 回归确认，隔离候选正式合并并清理后，原验收仍可满足下游依赖。
- 合法微信原生小程序可通过配置、清单和真实入口识别并路由到 `xy-web`。设计、移动和 QA 引用采用三端包内规范路径，生产 QA 按实际运行端和原型政策取证。既有移动设计及原始来源见 [通用 UI 质量与移动端开发规范](mobile-ui-guidance.md)。
